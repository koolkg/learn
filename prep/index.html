Java toolkit

Heaps (PriorityQueue)

// min-heap (default)
PriorityQueue<Integer> minHeap = new PriorityQueue<Integer>();

// max-heap
PriorityQueue<Integer> maxHeap =
    new PriorityQueue<Integer>(Collections.reverseOrder());

// objects, highest priority first
PriorityQueue<Task> pq = new PriorityQueue<Task>(new Comparator<Task>() {
    public int compare(Task a, Task b) {
        return Integer.compare(b.priority, a.priority);
    }
});
// peek O(1), add/poll O(log n), remove(obj) O(n)

TreeMap (sorted keys, red-black tree)

TreeMap<Integer, Integer> tm = new TreeMap<Integer, Integer>();
tm.firstKey();      // min      O(log n)
tm.lastKey();       // max      O(log n)
tm.floorKey(x);     // largest  <= x
tm.ceilingKey(x);   // smallest >= x
tm.higherKey(x);    // smallest >  x
tm.pollLastEntry(); // remove max
// ascending by default — NOT a heap

Stack / Queue / Deque

Deque<Integer> stack = new ArrayDeque<Integer>();
stack.push(x); stack.pop(); stack.peek();

Deque<Integer> queue = new ArrayDeque<Integer>();
queue.offer(x); queue.poll(); queue.peek();
// prefer ArrayDeque over Stack / LinkedList

Map-of-lists without lambdas

List<Integer> list = map.get(key);
if (list == null) {
    list = new ArrayList<Integer>();
    map.put(key, list);
}
list.add(value);
// same as: map.computeIfAbsent(key, k -> new ArrayList<>()).add(value);
Gotchas
  • Compare with Integer.compare(b, a), not b - a (overflow).
  • Compare boxed Integer with .equals() — == breaks outside −128..127.
  • Deep recursion (e.g. DFS on a 300×300 grid) can overflow the stack — use BFS or an explicit stack.
  • Math.abs(Integer.MIN_VALUE) is still negative — cast to long (Pow(x, n)).

System design · LinkedIn questions

Questions from codinginterview.com's LinkedIn list, expanded into interview-ready outlines. The first three are the main ones; the rest are shorter outlines. Click a question to expand it.

Framework for every question (~45 min)
  1. Requirements (5 min): functional, non-functional (latency, freshness, availability vs consistency), what's out of scope.
  2. Estimates (3 min): DAU, QPS (avg and peak), storage per day, read:write ratio.
  3. APIs and data model (5 min).
  4. High-level design (10 min): draw the boxes, walk one request end to end.
  5. Deep dives (15 min): the 2–3 hard parts — pick them yourself before the interviewer does.
  6. Scale, failure and trade-offs (5 min): sharding, hot keys, degradation, what you'd do next.
1. Design LinkedIn's feed ranking system core
ProblemPersonalized feed of posts, job updates and articles based on interests and connections. Key featuresReal-time aggregation from connections and followed entities; ranking by relevance, freshness and engagement likelihood; filter spam, low-quality and duplicate posts; optional reactions, comments, reshares.
  1. Requirements: p99 < 200 ms; fresh within ~1 min; availability over consistency.
  2. Estimates: ~150M DAU × 10 opens ≈ 17K QPS avg, ~50K peak; ~10M posts/day; celebrity accounts with 10M+ followers.
  3. Fan-out: hybrid — push post IDs to followers' inboxes for normal authors; pull at read time for authors over ~10K followers; push only to recently active users.
  4. Ranking funnel: candidate gen (inbox + celebrity pull + recommendations) → filter (seen, blocked, spam, dupes) → light ranker (~1000 → 200) → main ranker predicting P(click, comment, share, dwell) − P(hide) → re-rank (diversity, freshness, jobs/ads) → hydrate.
  5. Activity signals: client events (impressions, clicks, dwell) → Kafka → stream jobs update the Feature Store; data lake → retraining → A/B test.
  6. Storage: member graph in a sharded graph/KV store; inboxes in Redis-style cache; posts in a sharded KV store; Memcached for hydration.
  7. Quality: async spam/quality classifiers; SimHash/MinHash for near-duplicates; collapse multiple shares of one article.
  8. Reliability: shard by user ID; precompute feeds for highly active users; fall back to recency × connection strength if the ranker times out; snapshot the ranked list per session for stable pagination.
2. Design the LinkedIn messaging system core
ProblemReal-time messaging like LinkedIn Messaging / InMail with direct and group conversations. Key featuresSend/receive in real time; message history and delivery acknowledgment; typing indicators, read receipts, media; optional offline storage and spam filtering.
  1. Requirements: delivery < ~500 ms when online; no message loss; ordered within a conversation; multi-device sync; groups up to a few hundred members. Durability and ordering matter more here than in the feed.
  2. Estimates: ~50M daily messaging users × ~20 messages ≈ 1B messages/day ≈ 12K writes/s avg, ~40K peak; ~1 KB each ≈ 1 TB/day of text before replication.
  3. APIs: WebSocket send {client_msg_id, conversation_id, body, media_ref}; server events message, ack, typing, read; REST GET /conversations and GET /conversations/{id}/messages?before=cursor.
  4. Data model:
    • messages: partition key conversation_id, sort key message_id (time-ordered, Snowflake-style) — one partition read gives a page of history. Cassandra / Espresso-style wide-column store.
    • user_inbox: user_id → conversations sorted by last activity, with unread count and last-message preview (metadata stored separately for fast inbox loads).
    • conversation_members: members plus each member's last-read message_id — one pointer per member, not a read flag per message.
  5. Send flow: gateway → Message Service dedupes on client_msg_id (idempotency), assigns message_id, persists, updates inboxes, acks the sender ("sent"), then publishes to Kafka (partitioned by conversation_id to keep order). Delivery workers look up recipients' gateways in the presence store and push; offline users get APNs/FCM/email.
  6. Real-time transport: WebSockets (long polling as fallback). Gateways are stateful; a Redis presence map tracks user → gateway(s). On reconnect, the client sends its last-seen message_id and pulls anything missed — this is also how multi-device sync works.
  7. Delivery semantics: at-least-once delivery + client-side dedupe by message_id = effectively once. Receipts: sent (persisted) → delivered (device ack) → read (advance last-read pointer).
  8. Typing indicators / presence: ephemeral, never persisted, throttled (e.g. one event per 3 s), sent through pub/sub between gateways.
  9. Groups: fan-out on write to each member's inbox for small groups; for very large groups, fan out on read.
  10. Media: client uploads to blob storage with a presigned URL; the message carries only a reference; served via CDN; virus/abuse scanning async.
  11. Security: TLS in transit, encryption at rest with per-tenant/managed keys. Discuss the trade-off of end-to-end encryption: it blocks server-side spam filtering and search.
  12. Spam / InMail: InMail to non-connections costs credits; rate limits per sender; classifiers on Kafka; block/report; quarantine folder.
  13. Failure cases: gateway dies → clients reconnect with jittered backoff and resync by cursor; hot conversation → partition by conversation_id + bucket; region failover with async replication.
3. Design a job recommendation system core
ProblemRecommend relevant jobs based on profile, activity and preferences. Key featuresReal-time and batch recommendations; matching on location, skills, interests and engagement signals; feedback loop from user interaction.
  1. Requirements: "Jobs for you" page and job-alert emails; new jobs recommendable within minutes; hard constraints always respected (location/remote, job type, closed jobs, already applied). It's a two-sided marketplace — good for the member and the recruiter (qualified applicants, no flooding of a few popular jobs).
  2. Estimates: tens of millions of open jobs; hundreds of millions of members; ~20–50M daily job-page loads → a few thousand QPS, plus daily batch for alerts.
  3. Storage: job postings and member profiles in scalable document stores; Feature Store for signals; vector index for embeddings; precomputed recommendation lists in a KV cache.
  4. Candidate generation (several sources merged):
    • Content-based: match profile title, skills, seniority, location against job fields (search index).
    • Embeddings / semantic match: turn each member and each job into a list of numbers so that similar ones end up close together; find the nearest jobs with an approximate nearest-neighbor (ANN) lookup in a vector DB. Catches "Platform Architect" ≈ "Principal Infrastructure Engineer".
    • Collaborative filtering: "members similar to you applied to / saved these jobs".
    • Session signals: jobs similar to what you just viewed or searched.
  5. Filtering layers: location/remote, job type, expired or filled, already applied/dismissed, eligibility rules.
  6. Ranking: predict P(apply) and P(recruiter engages / good match), combine with freshness. Re-rank for diversity (cap per company), promoted jobs, and to spread applicants across jobs.
  7. Batch vs real-time: Spark jobs nightly recompute member embeddings and candidate lists (job alerts come from here). Newly posted jobs stream through Kafka, get embedded and indexed within minutes. Online ranking uses fresh session features.
  8. Feedback loop: impressions, clicks, saves, applies, "not interested", recruiter responses → Kafka → features and retraining. Correct for position bias (top results get clicked just for being on top).
  9. Cold start: new member → content-based from profile and stated preferences; new job → content and embedding match until it has engagement.
  10. Responsible AI: exclude protected attributes and proxies, audit outcomes by group, explain "why this job" — a natural place to bring in governance experience.

Additional system design questions

4. People You May Know (PYMK)

Goal: suggest new connections using mutual contacts, interaction history and profile similarity.

  • Candidates: friends-of-friends (2-hop walk with mutual-connection counts), same company/school/time overlap, imported address-book contacts, people who viewed your profile, members who searched for you.
  • Hard part: 2-hop explosion — a member with 30K connections has millions of 2-hop neighbors. Cap and sample high-degree nodes; precompute offline.
  • Pipeline: daily Spark job over the graph produces top-N candidates per member → KV store; real-time triggers (new connection, job change) refresh a member's list.
  • Ranking: predict P(invite sent) × P(invite accepted) — optimizing only for sends creates spammy invites.
  • Filters: already connected, pending invite, blocked, previously dismissed; privacy settings.
  • Graph storage: adjacency lists sharded by member ID, cached; graph partitioning to keep neighbors co-located where possible.
5. LinkedIn Live (live streaming)

Goal: live video with interactive comments, reactions and delay buffering.

  • Ingest: broadcaster sends RTMP/SRT to the nearest ingest server.
  • Transcode: into an adaptive bitrate ladder (1080p/720p/480p/audio), cut into 2–6 s segments (HLS/DASH).
  • Distribute: origin → CDN edges → players. Low-latency HLS gives ~3–5 s; WebRTC gives sub-second but costs far more at scale.
  • Delay buffering: a deliberate 10–30 s delay gives moderation time to cut a stream and smooths network jitter.
  • Comments and reactions: pub/sub fan-out to viewers via WebSocket. For huge audiences, sample comments and send aggregated reaction counts every ~1 s instead of every event.
  • After the stream: record to blob storage → VOD replay; post into followers' feeds; notify followers when going live.
6. Notifications system

Goal: deliver relevant, timely notifications across web, mobile and email without overloading users.

  • Flow: event producers (likes, comments, messages, job alerts) → Kafka → Notification Service → per-channel workers (APNs, FCM, email, in-app) → delivery tracking.
  • Dedupe and idempotency: event ID + recipient as an idempotency key; retries won't double-send.
  • Aggregation: batch "Alice and 12 others liked your post" within a time window instead of 13 pushes.
  • Overload control: per-user preferences, daily caps, quiet hours/time zones, priority tiers (a message from a connection beats "someone viewed your profile"). A ranking model can decide which notifications are worth sending.
  • Channel selection: in-app always; push if the user is not active in the app; email digest for low priority.
  • Reliability: retries with backoff, dead-letter queue, provider failover; in-app notification store per user (sorted by time, unread count).
7. URL shortener (lnkd.in)

Goal: short links like lnkd.in/xyz with analytics, expiration and custom aliases.

  • Key generation: base62 of a unique ID — each app server takes a range of IDs from a counter service (or a Key Generation Service with pre-made keys). 7 base62 chars ≈ 3.5 trillion keys. Avoid hashing the URL (collisions).
  • Storage: KV store short_key → {long_url, owner, created, expires_at}; heavily read, so cache hot keys (Redis/CDN edge).
  • Redirect: 302 (temporary) if you need every click counted; 301 is cacheable by browsers and loses analytics.
  • Analytics: log click events asynchronously to Kafka → stream aggregation (clicks by time, country, referrer); never block the redirect on analytics.
  • Expiration: TTL in the store plus a lazy check on read; background cleanup.
  • Custom aliases: uniqueness check on write; reserved words.
  • Safety: scan target URLs for malware/phishing on creation and periodically; rate-limit creation.

In the room (coding round)

  1. Clarify (2–3 min): input sizes, duplicates, negatives, empty input, what to return on ties.
  2. Example: walk one small example by hand; agree on expected output.
  3. Brute force first: state it and its Big-O in one sentence.
  4. Optimize: name the pattern (sliding window, two pointers, heap, BFS, DP…) and the target complexity from the input size.
  5. Code: clean helper methods, meaningful names, no lambdas needed.
  6. Test: trace your example, then edge cases (empty, one element, all same, max values).
  7. Follow-ups: LinkedIn often extends design problems (e.g. "now support duplicates", "make it thread-safe", "what if this runs across machines").
